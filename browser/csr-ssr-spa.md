# CSR / SSR / SPA 정리

CSR, SSR, SPA는 프론트엔드 렌더링 방식과 애플리케이션 구조를 설명할 때 자주 함께 등장하는 개념이다.

하지만 셋은 완전히 같은 분류가 아니다.

- SPA(Single Page Application): 애플리케이션 구조
- CSR(Client-Side Rendering): 렌더링 주체가 클라이언트인 방식
- SSR(Server-Side Rendering): 렌더링 주체가 서버인 방식

즉, **SPA는 앱 구조에 가까운 개념이고, CSR/SSR은 화면을 어디서 렌더링하느냐에 대한 개념**이다.

## 먼저 관계부터 이해하기

자주 헷갈리는 이유는 다음 조합이 많이 나오기 때문이다.

- SPA + CSR: React, Vue 같은 클라이언트 중심 앱
- SPA + SSR: Next.js 같은 프레임워크에서 첫 화면은 서버에서 렌더링하고 이후는 SPA처럼 동작

즉, SPA와 CSR은 자주 함께 쓰이지만 완전히 같은 말은 아니다.

## 1. SPA(Single Page Application)

SPA는 **초기 진입 시 하나의 HTML 페이지를 불러오고, 이후 화면 전환은 전체 페이지 새로고침 없이 JavaScript로 처리하는 방식**이다.

전통적인 MPA(Multi Page Application)는 페이지 이동마다 새로운 HTML 문서를 서버에서 다시 받지만, SPA는 필요한 데이터만 받아서 현재 페이지를 갱신한다.

### 특징

- 페이지 전환 시 전체 새로고침이 적다
- 사용자 경험이 앱처럼 부드럽다
- 라우팅을 클라이언트에서 처리하는 경우가 많다
- 초기 JavaScript 번들 크기에 영향을 많이 받는다

### 장점

- 화면 전환이 빠르고 자연스럽다
- 상태 관리가 유리하다
- 복잡한 인터랙션이 많은 서비스에 적합하다

### 단점

- 초기 로딩 부담이 커질 수 있다
- CSR만 사용하는 경우 초기 HTML이 비어 SEO에 불리할 수 있다
- 브라우저에서 처리할 JavaScript 양이 많아질 수 있다

## 2. CSR(Client-Side Rendering)

CSR은 **브라우저가 JavaScript를 내려받아 실행한 뒤 화면을 그리는 방식**이다.

서버는 보통 비어 있거나 최소한의 HTML과 JavaScript 번들을 내려주고, 실제 UI 렌더링은 클라이언트에서 수행한다.

### 동작 흐름

1. 브라우저가 기본 HTML을 받는다
2. JavaScript 번들을 다운로드한다
3. JavaScript가 실행된다
4. 데이터 요청 후 화면을 렌더링한다

### 장점

- 한 번 앱이 로드되면 이후 상호작용이 빠르다
- 프론트엔드와 백엔드 역할 분리가 명확하다
- 풍부한 인터랙션 구현에 유리하다

### 단점

- 초기 화면 표시가 늦어질 수 있다
- JavaScript 로딩/실행이 느리면 사용자 체감 성능이 나빠진다
- SEO 대응이 SSR보다 불리할 수 있다

### 적합한 경우

- 로그인 후 사용하는 대시보드
- 관리자 페이지
- SEO보다 사용자 인터랙션이 중요한 서비스

## 3. SSR(Server-Side Rendering)

SSR은 **서버에서 HTML을 완성해서 내려주고, 브라우저는 이를 바로 보여주는 방식**이다.

사용자는 JavaScript가 모두 실행되기 전에도 완성된 HTML을 먼저 볼 수 있다.

### 동작 흐름

1. 사용자가 페이지를 요청한다
2. 서버가 데이터를 조회한다
3. 서버가 HTML을 생성한다
4. 브라우저가 완성된 HTML을 먼저 렌더링한다
5. 이후 JavaScript가 연결되며 상호작용 가능 상태가 된다

이 마지막 과정을 보통 **하이드레이션(Hydration)** 이라고 부른다.

### 장점

- 초기 화면 표시가 빠를 수 있다
- 검색 엔진이 HTML 내용을 읽기 쉬워 SEO에 유리하다
- 저사양 기기에서도 첫 화면 체감이 나아질 수 있다

### 단점

- 서버 부담이 증가할 수 있다
- 구현 복잡도가 올라간다
- 페이지 요청마다 서버 렌더링 비용이 발생할 수 있다

### 적합한 경우

- 검색 유입이 중요한 서비스
- 블로그, 커머스, 콘텐츠 페이지
- 첫 화면 노출 속도가 중요한 서비스

## CSR과 SSR 비교

| 항목 | CSR | SSR |
| --- | --- | --- |
| 렌더링 주체 | 브라우저 | 서버 |
| 초기 화면 표시 | 상대적으로 느릴 수 있음 | 상대적으로 빠를 수 있음 |
| 이후 페이지 전환 | 빠르고 부드러움 | 구조에 따라 다름 |
| SEO | 불리할 수 있음 | 유리함 |
| 서버 부담 | 상대적으로 적음 | 상대적으로 큼 |
| 클라이언트 부담 | 큼 | 초기 표시 기준으로는 상대적으로 분산 가능 |

## SPA와 SSR은 같이 쓸 수 있다

많이 하는 오해는 다음 두 가지다.

### 1. SPA = CSR이다?

완전히 같지는 않다.

SPA는 한 페이지 기반으로 동작하는 애플리케이션 구조이고, 그 SPA의 첫 렌더링을 CSR로 할 수도 있고 SSR로 할 수도 있다.

### 2. SSR이면 SPA가 아니다?

그것도 아니다.

예를 들어 Next.js 같은 구조에서는 **첫 요청은 SSR로 HTML을 만들고, 이후 클라이언트에서 라우팅하며 SPA처럼 동작**할 수 있다.

즉, **SSR과 SPA는 배타적인 개념이 아니라 조합 가능한 개념**이다.

## 실무에서의 선택 기준

### CSR이 잘 맞는 경우

- 로그인 후 내부 서비스
- 대시보드, 관리자 화면
- 검색 유입보다 사용성/상호작용이 더 중요한 경우

### SSR이 잘 맞는 경우

- SEO가 중요한 서비스
- 첫 화면 콘텐츠 노출이 중요한 경우
- 상품 상세, 블로그, 랜딩 페이지 같은 공개 페이지

### 혼합 방식이 많은 이유

실무에서는 한 가지만 고집하기보다 섞어 쓰는 경우가 많다.

- 공개 페이지: SSR 또는 정적 생성
- 로그인 이후 앱 영역: CSR

이렇게 나누면 SEO와 사용자 경험을 함께 챙기기 쉽다.

## 자주 하는 실수

### 1. SPA와 CSR을 같은 개념으로 설명함

SPA는 앱 구조, CSR은 렌더링 방식이다.

### 2. SSR이면 무조건 빠르다고 생각함

첫 화면은 유리할 수 있지만, 서버 렌더링 비용과 하이드레이션 비용도 고려해야 한다.

### 3. SEO만 보고 무조건 SSR을 선택함

서비스 특성상 검색 유입이 거의 없고 내부 사용자가 대부분이면 CSR이 더 단순하고 적절할 수 있다.

## 정리

- SPA는 하나의 페이지 기반으로 동작하는 애플리케이션 구조다.
- CSR은 브라우저가 JavaScript로 화면을 렌더링하는 방식이다.
- SSR은 서버가 HTML을 만들어 먼저 내려주는 방식이다.
- 실무에서는 둘 중 하나만 고르기보다 페이지 성격에 따라 혼합하는 경우가 많다.

## 면접 답변용 한 줄 정리

SPA는 단일 페이지 기반 앱 구조이고, CSR은 클라이언트가 렌더링하는 방식, SSR은 서버가 HTML을 만들어 먼저 내려주는 방식이며, 실제 서비스에서는 SEO와 사용자 경험에 따라 이들을 조합해 사용한다.
